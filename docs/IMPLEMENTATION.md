- Sidebar counters are activity indicators, not totals or pending-work counts. Documents counts distinct currently accessible records changed by other staff; Incoming counts new pending/accepted handoffs; Outgoing counts distinct sent records with new handoff actions by other staff. Opening that tab marks its current activity read, independently of other tabs; filtered/history views also count as opening the tab. Stored read cursors are scoped to user/office/tab, increase monotonically and survive new sessions. Prefetch, dashboard/detail visits and the activity-poll endpoint do not mark tabs read. The poll endpoint returns counts only and does not replace the form-validation return URL. Unseen badges refresh every 30 seconds on visible pages and when focus returns. Existing custody/confidentiality policies are retained.

- The sending office retains custody during a pending transfer. Only one transfer may be pending. The destination may acknowledge or reject; the sender may cancel before acknowledgment. Rejecting/cancelling restores the document's previous processing status.
- Staff can read ordinary records held by their office or with a pending transfer to their office. Confidential records require current custody or a pending incoming transfer; admins do not bypass confidential office restrictions. Admins can view ordinary records across offices. Actions require current custody; incoming staff may only acknowledge/reject until acceptance.
- Statuses are fixed for v1. Received -> in progress/on hold/completed/cancelled; in progress -> on hold/completed/cancelled; on hold/returned -> in progress/cancelled; completed -> released. Returned is reached by acknowledging a return-for-correction handoff, not by a standalone status update. Admins in the owning office may reopen completed/released/cancelled documents to in progress, with a reason. Forwarding/returning is separate from this transition table and is forbidden during a hold or terminal state.
- Return for correction requires a responsible active office and a reason. The previous sending office is preselected when available, falling back to the originating office when eligible. Sender custody remains until acknowledgment; rejection/cancellation restores the previous state. Every movement remains in its sender's Outgoing history and accepted movements remain in Incoming Received history. Former offices receive a minimal movement summary; full document access and confidential subject search still use existing visibility rules.
- Processing targets count calendar days in Asia/Manila. Holds do not pause deadlines. No target means no deadline. Store timestamps in UTC; display Asia/Manila. Reports use received_at for date scope and the first completed_at for completion duration; reopening clears completion/release timestamps so a later completion starts the current cycle's result.
- Public lookup returns only the reference, generic category, mapped safe status, update timestamp and a citizen progress timeline containing fixed public titles, mapped statuses and original event timestamps. Never expose internal remarks, office names, names or attachments; free-text event details are not used to generate public titles.
- By explicit user request on 19 October 2026, new non-confidential registrations automatically issue eight-character random access codes, formatted as two groups of four on receipts. Hashes verify lookups; separately encrypted copies support authorized current-custodian reprints after refresh/login. Codes never enter shared flash props, list/history props, events, audit metadata or public responses. Lookup ignores letter case, spaces and dashes and remains throttled. Existing hexadecimal codes remain valid, while existing records/codes are not automatically enabled or replaced. Confidential documents remain excluded. This user decision replaces the brief's original opt-in/one-time-display behavior.
- Password-reset email uses configured SMTP in deployment; local log mail is explicitly a development preview. A secure operator-only password-reset command provides recovery without SMTP.
- The administrator may initially have no office. Registration/routing require a real active office. Staff always require an active office. No self-registration or destructive self-account deletion.
- By explicit user request, this workstation now uses XAMPP's MariaDB 10.4.32 at port 3306. The earlier separate MySQL instance is no longer required. Existing data was copied and verified before switching; unrelated XAMPP databases were preserved.

## Switch to XAMPP database

The user explicitly replaced the PDF's MySQL 8 requirement with XAMPP's bundled MariaDB. Application and test connections use the native `mariadb` driver at port 3306. A full SQL backup and original environment files were saved before transfer. Every copied row, including encrypted values, password hashes, sessions and migration batches, matched the original source before cutover.

The first non-null TIMESTAMP in MariaDB 10.4 can acquire an implicit ON UPDATE clause. Receipt, transfer, event, public-code issue and audit dates now use explicit DATETIME values, with a compatibility migration for existing installations. Advisory bootstrap locking supports both MySQL and MariaDB.

A pre-existing damaged index in XAMPP's `mysql.db` privilege table blocked new schema grants. The affected Aria table files were backed up and checksummed before `REPAIR TABLE mysql.db QUICK`; a subsequent CHECK TABLE returned OK. Existing grants were retained and app/test accounts were added with access to their own schemas.

The portable-server launcher was removed. The old server's data and the migration backup are retained privately for recovery. Start the MySQL service in XAMPP to use this project.

Final switch verification: all operational records and APP_KEY still match the original instance after the compatibility migration. The testing account cannot SELECT from the application schema. All 48 tests (317 assertions) and PHP style checks pass against XAMPP MariaDB. The original server was shut down cleanly and its launcher removed; recovery files were retained.

Review results and optional details stay private. Assignment indicates responsibility without narrowing colleagues' existing office permissions. ## Staff notifications, 20 October 2026

The approved notification bell covers assigned handlers, incoming office handoffs and returns for correction. Individual recipient rows reference the originating workflow event and keep independent read/resolution dates. Creation and retirement happen within existing workflow transactions. Self-claims produce no alert; handoffs notify active members of the destination office. No historical alerts are backfilled. Opening the bell is read-only; Open document marks only the recipient's alert read and rechecks current access under the document lock. Mark all read uses the displayed ID snapshot so later arrivals stay unread. Neither read control changes custody, status, office work or sidebar read cursors.

Only currently actionable alerts are returned. Reassignment, finishing work and resolved handoffs retire their alerts. Acknowledged returns remain visible until processing resumes or custody changes; cancelling a pending movement restores the original applicable alert. Read alerts stay available while actionable, and ten-item pagination keeps older active alerts accessible. The feed and unread count refresh every 30 seconds on visible pages, on focus and when the bell opens. Public tracking omits the feed, and each request applies recipient, active-office and current document-visibility restrictions. References, fixed action text and event dates are the only document details displayed in the menu.
